# Архитектура AI-DND

## Границы системы

`domain` содержит статусы и правила переходов без зависимостей от FastAPI,
SQLite или конкретного LLM. `application` координирует use cases и транзакции.
`api` отвечает только за транспорт, DTO, авторизацию и преобразование ошибок.
`infrastructure` реализует хранение и runtime-механизмы. `integrations`
изолирует внешние AI/voice providers. `core` содержит конфигурацию и lifecycle.

Зависимости направлены внутрь:

```mermaid
flowchart TD
    API["api"] --> APP["application"]
    INFRA["infrastructure"] --> APP
    INTEGRATIONS["integrations"] --> APP
    APP --> DOMAIN["domain"]
    API --> CORE["core"]
    INFRA --> CORE
    INTEGRATIONS --> CORE
```

## Данные

SQLite является единственным source of truth. Включены foreign keys, WAL и
`busy_timeout`. Изменения схемы выполняет Alembic. Campaign revision защищает
подтверждение Observer proposal от устаревшего состояния; уникальные ключи
защищают sequence событий и ходов.

JSON — только версионированный формат обмена. Legacy importer сначала выполняет
полную валидацию и dry-run, а затем импортирует данные одной транзакцией.

## Realtime

Каждый WebSocket-клиент имеет собственную bounded queue. Событие сначала
сохраняется в БД с монотонным sequence, затем рассылается подписчикам.
Переподключение использует `last_sequence` и replay. GM получает public и GM
events, spectator — только public.

## Безопасность

GM bootstrap token хранится только в системной data directory. Bootstrap
обменивается на подписанную HttpOnly SameSite cookie. Spectator использует
read-only join code. В production CORS не нужен; dev origins перечисляются явно.

API формирует отдельные projections. Мысли текущего хода входят в публичную
spectator-проекцию по продуктовым правилам, но private notes, персональные хроники,
provider metadata и prompts никогда туда не попадают. В prompt другой модели
передаются только публичные действия; собственные прошлые мысли доступны лишь той
же модели-персонажу.

## LLM и jobs

Интеграция описана `LLMProvider`. Model profile задаёт model ID, JSON schema
capability и temperature. Вызовы выполняются как durable BackgroundJob с
ограниченной конкурентностью. Структурированный ответ валидируется Pydantic;
после двух корректирующих повторов job завершается ошибкой без изменения
кампании.

### Завершение игрового события

Завершение выполняется в две фазы. Первая команда переводит событие из `active` в
`finalizing` и запускает durable job. Архивариус объединяет только общую
фактологическую хронику. Затем каждая модель-игрок отдельно обновляет личные заметки
своего персонажа, используя его `model_id`, прежние заметки, публичные действия и
только собственные мысли. Общий результат остаётся черновиком и не изменяет память.
GM может отредактировать его, повторить генерацию или ввести итог вручную.

Только подтверждение GM одной транзакцией:

1. проверяет revision события и точный набор игроков-участников;
2. записывает объединённую хронику всем участникам;
3. заменяет private notes только игрокам-участникам;
4. сохраняет подтверждённый архивный результат для аудита;
5. переводит событие в `archived`.

При timeout, недоступности провайдера, невалидном JSON или перезапуске интерфейса
событие остаётся `finalizing`, а ходы и прежняя память остаются в SQLite. Активный лог
исчезает из игровой проекции только после успешного commit; сами ходы не удаляются и
остаются частью истории события.

Сжатие контекста хранит конспект старой части активного события отдельно от исходных
ходов. Промпты игроков и финализации получают конспект и последние десять ходов,
а полный неизменённый журнал остаётся в SQLite для аудита.

## Frontend

`/gm` и `/spectator` — отдельные lazy chunks. TanStack Query хранит server
state, Zustand — только выбранного персонажа и локальное audio/UI state.
Формы используют RHF + Zod. Контент модели рендерится обычными React nodes.
